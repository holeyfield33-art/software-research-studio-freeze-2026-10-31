# Build sequence, research limits and acceptance

## What is established

The archival baseline is intact: 715 records across ten collections, including 601 relationships and ten software types. It supports a common lifecycle and conditional practices. The independent reports add proposals and critiques concerning UX artifacts, implementation contracts and evidence integrity. These are inputs to synthesis, not interchangeable proofs.

UNIVERSAL-001 establishes a reviewable proposed system boundary, logical modules, record inventory, lifecycle and development sequence. Exact references in the generated mapping resolve locally. No universal runtime, applicability engine or executable schema is implemented by this checkpoint.

## Gaps to resolve

| Gap | Current evidence / limitation | Required next result |
|---|---|---|
| Applicability correctness | 003R independent audit identifies wrong rationale, contradictions, malformed-input failures and over-selection | Explicit predicate semantics, decision traces and adversarial fixtures; decide whether to repair or replace legacy evaluator behind a common interface |
| Uneven domain depth | Ten category records do not demonstrate exhaustive platform expertise; only three pinned reference projects exist | Per-domain capability inventory; declare unsupported decisions and commission bounded research where necessary |
| UX research lineage | Gemini's eight proposed `003R-*` IDs are absent from frozen registry; quantitative claims remain unverified | Preserve proposals in a new namespace, map concepts to existing evidence or record unsupported gaps |
| Complete project model | Source records list useful inputs and artifacts but do not define a running Studio state system | Versioned schemas, identity rules, reference semantics and migrations |
| Artifact consistency | Traceability links alone do not prove implementation or detect all semantic drift | Dependency and invalidation rules plus independent property checks |
| Operational lifecycle | General maintenance/release guidance is not a full incident or distribution implementation | Concrete release, recovery and incident contracts with conditional adapters |
| Authority and recovery | Research recommends bounded actions but runtime enforcement is unimplemented | Explicit capability enforcement and interruption/retry semantics |
| Evaluation validity | No improvement percentage or universal competence established | Diverse held-out project scenarios and measured workflow trials after core behavior exists |

## Sequenced milestones

| Milestone | Deliverable | Acceptance / stop condition |
|---|---|---|
| M0: universal synthesis (this checkpoint) | Architecture, lifecycle, gaps and exact research mapping | References resolve; originals unchanged; proposals distinguished from executed results |
| M1: project contracts | Schemas for facts, decisions, artifacts, tasks, evidence, findings and gates; examples for new/existing projects | Reject dangling references, conflicting facts treated as known, stale evidence marked current, and unauthorized permission inheritance |
| M2: applicability and planning | Narrow deterministic decision core and dependency-aware planner | Counterfactual facts change decisions and reasons consistently; unknown/conflicting inputs produce explicit abstention; no automatic use of legacy profiles |
| M3: complete manual workflow | File-based end-to-end project packet, task handoff, evidence recording and resume | A different operator can continue; failures persist; a changed prerequisite invalidates dependent claims |
| M4: bounded execution adapters | At least one actual ecosystem integration with inspect/execute/verify capability declarations | Allowed actions enforced, retries bounded, interruption recorded, independent acceptance evidence tied to candidate |
| M5: broader specialization | Profile-specific artifacts and supported adapters driven by capability gaps | Additional project types use shared contracts without mandatory UI, HTTP, database or agent infrastructure |
| M6: comparative evaluation | Preregistered tasks spanning multiple categories and new/existing projects, held-out acceptance criteria | Report completion, correctness, regressions, human intervention, time and total cost; no productivity claim before measurement |

The first implementation is a small complete lifecycle workflow, not every adapter at once. Proposed initial scenario set: new local CLI, existing library compatibility change, authenticated API change, UI interaction correction and data pipeline recovery. These are evaluation fixtures, not architectural targets. Include cross-category and unknown-category cases; held-out scenarios must not be used to hard-code passing decisions. SurfaceTrace may later contribute a UI maintenance case alongside others.

Research source verification and platform-specific claims require separate evidence before enforcement. The inherited library contains summaries and publisher-specific guidance; reading a stored source record is not a new external-source audit. No standard certification is claimed.

## Next concrete work

M1 is next: define the minimum versioned project packet and its transition/invalidation semantics, then create representative positive and negative examples before implementing the validator. The validator verifies that contract, not universal development correctness. M2 must address the known selector weaknesses before automated recommendations are treated as dependable.
