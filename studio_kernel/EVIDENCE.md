# Signed evidence import and task acceptance

This continuation connects external execution attestations to the canonical kernel. It adds Ed25519 receipt verification, verified run import, retained proof bundles and task-bound acceptance proposals. No project command or deployment is executed by these commands.

## Trust boundary

The operator supplies a trusted public-key configuration separately from project records and receipt bundles. Each key is limited to listed purposes (`authority`, `run`, `review`, `release`), projects, subjects and logical scopes. Trust configuration also pins required release gate IDs, maximum receipt lifetime and revoked record hashes. Key removal revokes that issuer; record hashes can be revoked explicitly. Configuration must come from the operator's trusted control path, never from instructions inside a project or research document.

`receipts.py` defines the closed trust and receipt schemas. A receipt payload contains version, issuer, purpose, project ID, exact canonical record SHA-256 and issue/expiry timestamps. The Ed25519 signature covers the canonical payload bytes, including their LF terminator. Verification rejects altered records, unknown keys, purpose/project/subject/scope mismatches, future issue times, expired receipts, excessive lifetimes and explicit revocations. Private signing keys are never read or generated by the CLI. Tests generate temporary in-memory keys solely for synthetic fixtures.

A signature authenticates an authorized source's attestation; it does not prove that source was truthful or competent. Trusted host integration must actually enforce runtime capabilities, establish independent oracles and evaluate complete required checks. Public-key pinning supplies a concrete callback implementation, not a replacement for these responsibilities. Different issuers/role-limited keys should reflect the real trusted-host and independent-review boundaries.

The attested record determines the statement: an Authority receipt authenticates the grantor's exact scoped grant; an EvidenceRun receipt attests actual execution, bound packet/oracles, environment, outputs and observed result; an accepted DesignDecision review receipt authenticates that exact review; a ReleaseDecision receipt attests owner approval, required gate completeness and actual support/recovery evidence. No receipt changes the underlying canonical record schema.

## Commands

```text
python -m studio_kernel validate records.json --project example --candidate candidate.json --artifacts evidence-root --trust-config trusted-public-keys.json --receipts host-receipts.json
python -m studio_kernel import-evidence runs.json --project example --store history.sqlite --expected 1 --candidate candidate.json --actor operator --trust-config trusted-public-keys.json --receipts host-receipts.json --artifacts evidence-root
python -m studio_kernel accept --project example --store history.sqlite --candidate candidate.json --task-ref task-ref.json --policy-ref policy-ref.json --review-ref review-ref.json --gate-id gate.unit_integration_execution --created-at 2026-11-01T00:00:00Z --trust-config trusted-public-keys.json --artifacts evidence-root
python -m studio_kernel status --project example --store history.sqlite --trust-config trusted-public-keys.json --artifacts evidence-root
```

Record-reference files contain exact `id`, `revision` and `sha256`. `runs.json` is a list of canonical EvidenceRun records. Timestamp and state revision in the example must be supplied for the actual project; they are not auto-refreshed. Omit trust inputs to keep ordinary validation conservative. Supplying receipts without the required operator trust configuration is rejected.

## Import and retention

`import-evidence` resolves the full record history, then verifies the imported runs and their dependency closure. It checks exact references, candidate freshness, authenticated grants and run receipts, oracle binding and real output bytes. Imports are limited to executed PASS or FAIL observations. An authentic failure is recorded as a failure, never turned into successful task acceptance. Unsupported or unsigned observations can still be preserved through the generic `record` command, but they do not become verified evidence.

Before committing imported observations, the command writes a public proof bundle under `<history-file>.receipts/<canonical-bundle-sha256>.json`. The canonical ChangeEvent reason binds that digest. Reopening loads referenced proofs and verifies their content digests; current signatures, keys, expiry and revocations are evaluated again using the current operator configuration. Carry both the history file and its proof directory when transferring this checkpoint. The artifact root must also remain available for output verification.

Proof files are prepared before the SQLite transaction. An interrupted import may leave an unreferenced proof file, but it cannot create a committed observation without its proof being prepared first. Unreferenced files grant no authority. Corrupt or missing referenced proofs fail visibly; they are not silently replaced. This is not an adversarial power-loss/filesystem qualification or a tamper-proof external anchor.

## Task acceptance

`accept` selects current EvidenceRun records for the exact TaskPacket hash and candidate. It requires a signed accepted policy and a signed accepted review whose `derived_from` includes that exact task and every evaluated execution record. A review of the plan alone cannot approve later output. Record the independently signed review after the execution records exist. The review owner must differ from the task builder. Hard prerequisite tasks need current passing task-bound gates; unadjudicated conditional dependencies block acceptance. Scope isolation retains all revisions of participating IDs so an obsolete input cannot be hidden by omitting history.

The kernel rechecks signatures, authority, artifact bytes, oracles and staleness. Verified failed runs produce a FAIL gate; no current passing execution produces INCOMPLETE; only verified current passing evidence yields a PASS gate proposal. Gate review validation now also requires a signed accepted task-bound independent review, so the older existence-only review stub cannot satisfy it.

Acceptance returns a canonical GateDecision proposal without mutating history or releasing software. Preserve/record the returned gate through the existing explicit history operation. Effective release approval additionally requires the operator-pinned full gate-ID set, all current gates passing on one candidate, current release authority and a signed release review. Historical HOLD revisions stay queryable while the latest decision of an identity controls its current disposition.

## Verification and limits

Tests cover signature forgery and record mutation, incorrect issuer/key/project/purpose/subject/scope, time and revocation constraints, missing release gates, unsigned/unbound review rejection, corrupt output rejection, authentic failure import, proof retention/reopen/corruption and the real CLI import→read-only acceptance path. No private keys, live grants or project execution results are published by these tests.

Still pending: a real enforcing host adapter and signing service, robust cross-machine trust administration, an explicit gate policy/oracle completeness evaluator beyond authenticated host assertions, event-level independent anchors, signed-proof renewal, full task scheduling/replanning and real end-to-end lifecycle trials. Candidate identity and output environments are attested/operator-supplied, not independently reconstructed from an arbitrary checkout. Product integration and automatic selector promotion remain unapproved and unproven.
